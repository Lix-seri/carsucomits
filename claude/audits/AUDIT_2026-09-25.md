## Critical

### C1 — Anyone could sign in as any user, including the admin
- **Where:** `src/lib/session.ts` (before `5174b12`)
- **Problem:** the session cookie was `base64(JSON.stringify({userId, role, …}))` with no signature, and `AUTH_SECRET` was never read. Writing `{"userId":"<admin id>","role":"ADMIN"}` into the cookie gave full admin access.
- **Fix:** HMAC-SHA256-signed token `{uid, role, exp}`; the user is re-loaded on every request (ADR 0001).
- **Status:** **Fixed** in `5174b12`. Verified:
  - 6 unit tests cover a forged role, the legacy format, expiry and a wrong secret;
  - an end-to-end script confirmed a forged admin cookie is redirected and a tampered signed cookie is rejected.

## High

### H1 — Bans and suspensions didn't take effect until the cookie expired (7 days)
- **Where:** `src/lib/session.ts` (before `5174b12`)
- **Problem:** `getSession()` trusted the cookie without looking up the user. Status and role changes were ignored.
- **Fix:** `getSession()` loads the user and returns `null` for `BANNED`/`SUSPENDED`.
- **Status:** **Fixed** in `5174b12`. Verified: a banned user's existing cookie gets 401 on the next request.

### H2 — An approved deliverable makes the commission impossible to complete
- **Where:**
  - `src/features/ratings/server.ts:97`
  - `src/app/(dashboard)/hub/page.tsx:145`
  - `src/app/(dashboard)/dashboard/page.tsx`
- **Problem:**
  - Uploading a deliverable moves the commission to `AWAITING_REVIEW`.
  - Approving it leaves it there.
  - `/complete` only accepts `IN_PROGRESS`, and "Mark Complete" is only shown for `IN_PROGRESS`.

  So the normal path (deliver → approve → complete) dead-ends.
- **Fix:** allow completion from `AWAITING_REVIEW` too, and show "Mark Complete & Review" for both states.
- **Status:** **Fixed** in `9766528`. The commission page also gains the button. Test: `e2e/audit-fixes.spec.ts` H2.

### H3 — The home page is fake data with broken links, including a prohibited listing
- **Where:**
  - `src/features/landing/landing-content.tsx:15`
  - `src/features/landing/mock-data.ts:29`
- **Problem:**
  - Every listing on `/` comes from a hard-coded array.
  - "Apply Now" goes to `/commission/c1` etc., which 404.
  - One of the fake listings is "Research Paper Writing", the exact academic work item 9 bans.
- **Fix:** render the latest real open commissions; delete the mock data and the mock card.
- **Status:** **Fixed** in `727cdd4`. Category cards now deep-link to `/browse?category=…`. Test: H3.

### H4 — No request validation: bad input causes 500s and unbounded writes
- **Where:** the 20 routes listed in `scripts/check-structure.mjs` (`UNVALIDATED_BASELINE`), for example `src/features/commissions/server.ts:63`
- **Problem:**
  - Crashes: `fareMin: "abc"` → `Number("abc")` → Prisma error → 500. `deadline: "tomorrow"` → Invalid Date → 500.
  - Nonsense data: `fareMax < fareMin` is accepted, as are deadlines in the past.
  - No length limits on titles, descriptions, messages, cover letters, report details or skill names.
  - Report `reason` accepts any string.
- **Fix:** a zod schema per endpoint in `features/<domain>/schemas.ts`. `jsonRoute` maps a `ZodError` to a 400 with a readable message (ADR 0007). The structure check's baseline must shrink to zero.
- **Status:** **Fixed** in `1b6e5b9`. The structure check's unvalidated-route baseline is empty. Verified by 14 schema unit tests and an e2e check that `fareMin: "abc"` → 400 `{ field: "fareMin" }`.

### H5 — The admin password is public, and re-seeding resets it
- **Where:** `prisma/seed.mjs:15`, `:24`; also the README, SETUP and DEPLOY docs (before the restructure)
- **Problem:**
  - `glen.licayan@carsu.edu.ph` / `123456` is committed in four files.
  - Running the seed again silently resets the admin's password to `123456`.
  - Combined with H6, the admin account is trivially guessable.
- **Fix:**
  - The seed takes `SEED_ADMIN_PASSWORD` (12+ characters), or generates a random one and prints it once.
  - It never resets an existing admin's password.
  - The docs stop printing a password.
- **Status:** **Fixed** in `c218d2d`. **Action for the owner:** any database seeded before this still has the old public password. Re-run `npm run db:seed` with `SEED_ADMIN_PASSWORD` set.

### H6 — Unlimited password guessing
- **Where:** `src/features/auth/server.ts:21`
- **Problem:** there's no throttling or lockout on `/api/auth/login`. The password minimum is 8 characters, and the seeded admin's is 6.
- **Fix:**
  - Record failed logins in the audit log (`LOGIN_FAILED`).
  - Refuse a login for an email with 5 failures in the last 15 minutes, answering 429 with a clear message.
  - Database-backed, so it works across serverless instances.
- **Status:** **Fixed** in `ddd77c9`. The count resets on a successful sign-in, and account status is only revealed after a correct password. Tests: H6 ×2.

### H7 — MFA can be switched off without the password
- **Where:** `src/features/auth/server.ts:77`
- **Problem:** `POST /api/auth/mfa/setup` sets `mfaEnabled: false` and replaces the secret. Anyone holding a session (a shared computer, a stolen cookie) can turn MFA off, bypassing `/mfa/disable`, which asks for the password.
- **Fix:** refuse setup while MFA is enabled (409); turning it off must go through `/mfa/disable`.
- **Status:** **Fixed** in `cbee183`. Test: H7 (enables MFA with a real TOTP code, then setup → 409).

### H8 — Reported users can see who reported them
- **Where:**
  - `src/features/reports/server.ts:31`
  - `src/features/reports/reports-view.tsx:87`
- **Problem:** "Reports about you" shows the reporter's full name, and the API returns it. That invites retaliation in exactly the harassment and scam cases reports exist for.
- **Fix:** don't include the reporter in `aboutMe`; show "A user reported you".
- **Status:** **Fixed** in `12b222c`. Test: H8.

### H9 — Signed-in and admin screens are unusable on phones
- **Where:**
  - `src/components/layout/dashboard-sidebar.tsx:33` (`w-64 shrink-0`)
  - `src/components/layout/admin-sidebar.tsx:22` (`w-60 shrink-0`)
  - `src/components/layout/dashboard-topbar.tsx`
- **Problem:**
  - Both sidebars are always visible at full width. On a Pixel 7 (412 px) every signed-in page renders about 800 px wide: the 256 px sidebar plus the content. The user has to scroll sideways, and the sidebar takes most of the first screen.
  - The topbar (search, Filter, bell, Post) is squeezed.
  - Seen in the Phase 3 screenshot `mobile/user-dashboard.png`.
- **Fix:** below `lg`, hide the sidebar behind a menu button (a drawer). The topbar collapses Post and Filter into icon buttons.
- **Status:** **Fixed** in `b104755`.
  - A shared `AppShell` provides the drawer.
  - The no-op Filter button and the fake admin bell are removed.
  - Messages shows one pane at a time on phones; the public header gets a menu.
  - Tests: H9 (the drawer), plus every page check now fails if a page is wider than the real viewport. That check found two more overflows (the dashboard grid and the admin log lines), both fixed.

### H10 — False trust signals: everyone is shown as "Verified" with a 4.8 rating
- **Where:**
  - `src/app/(dashboard)/layout.tsx:18` (`rating: 4.8, verified: true`)
  - `src/app/(dashboard)/profile/page.tsx:31`, `:34`
  - `src/features/profile/profile-card.tsx:34`
  - `src/app/u/[id]/page.tsx` ("Verified" for any active user)
  - `src/app/about/page.tsx:8`
- **Problem:**
  - Every signed-in user sees "★ 4.8 · Verified" in the sidebar and "Verified Student · Student Employee" on their profile, whatever their real rating, role or verification.
  - The about page promises "CSU Email Verified … no fake accounts", but email verification was removed in `7d4237e`: any `@carsu.edu.ph` address can be registered by anyone (M12).
- **Fix:**
  - Show the real rating and the real role.
  - Remove "Verified" badges until real verification exists (Phase 5, item 6).
  - Correct the about page.
- **Status:** **Fixed** in `88fbe68`.

## Checked and fine

- **SQL injection:** all queries go through Prisma with parameters; there's no `$queryRaw`.
- **XSS:** React escapes all output; there's no `dangerouslySetInnerHTML`, and notification links are built server-side from ids.
- **CSRF:** the session cookie is `SameSite=Lax`, so cross-site POSTs arrive without it. The only CSRF-able action is GET logout (L4).
- **Secrets:** `.env` is git-ignored, `.env.example` holds placeholders only, and no tokens are in the repo.
- **Open redirects:** none; every redirect target is a fixed path.
- **Ownership checks:** every mutation that touches another user's data checks ownership in its service. The e2e suite covers accept by a non-owner (403), completion by a non-owner (403), deleting someone else's skill (404), and admin actions by a non-admin (403).
- **Tests:** there were none. There are now 24 unit tests and 15 Playwright tests, run on desktop and Pixel 7: 30 runs, of which 9 are skipped by design.
